# Приватность и безопасность TGWR 0.2

Этот документ описывает границы защиты TGWR, а не обещает невозможное. Он относится к desktop-приложению, которое обрабатывает личный Telegram Export на компьютере владельца.

## Что защищает приложение

- Экспорт Telegram читается локально; TGWR не просит пароль, код входа, сессию или токен Telegram и не отправляет переписки в сеть.
- Нормализованные сообщения, `report.json` и кэш лежат в локальном каталоге `userData` Electron. Их можно удалить внутри приложения командой «Стереть все данные».
- Electron запущен с `contextIsolation`, sandbox и без Node.js в renderer. Веб-интерфейс получает только ограниченный preload API, а не доступ к файловой системе или shell.
- У packaged-приложения включена отдельная строгая Content Security Policy: production renderer не может подключаться к `localhost`/WebSocket, загружать плагины, формы или вложенные страницы. Послабление для локального Vite-сервера действует только в dev-режиме.
- Папку импорта можно передать worker только после выбора через системный диалог в текущем сеансе.
- PNG/PDF можно записать только в папку, которую пользователь выбрал в текущем сеансе. Имя ограничено `.png` и `.pdf`; traversal запрещён. Запись идёт в случайный временный файл внутри этой папки и затем атомарно заменяет цель, поэтому существующий симлинк не разыменовывается.
- Все новые навигации окна отменяются. Разрешённые `http(s)`-ссылки открываются внешним браузером; новое окно внутри приложения не создаётся.
- Полное удаление сначала останавливает worker, а потом очищает основную и legacy-базы, WAL/SHM, отчёты, кэш и временный staging-импорт. Worker запускается заново только после этой операции.
- Внешние GitHub Actions зафиксированы точными commit SHA. Установщики получают SHA-256 ведомость, а версия тега проверяется против package/lock/worker/UI/README до сборки.
- Packaged smoke запускает приложение во временном изолированном `userData` и удаляет его после проверки, поэтому CI и локальный release gate не читают и не меняют настоящий Wrapped пользователя.

## Входные данные и модель угроз

Telegram Export считается недоверенным входом: имена, текст, HTML и структура файлов могут быть повреждёнными или специально сформированными. Parser не исполняет текст сообщений как код; React выводит данные как текст, а не как HTML. Повреждённые части должны закончиться ошибкой или предупреждением, не заменяя предыдущую успешную базу: импорт идёт через отдельную staging-БД и публикуется только после полного успеха.

TGWR защищает от случайных ошибок приложения и от попыток renderer выйти за предоставленные IPC-разрешения. Он не может защитить от человека или другой программы, уже имеющих доступ к той же учётной записи ОС: такой субъект способен прочитать `userData`, перехватить экран, изменить выбранный каталог или удалить файлы вне TGWR.

## Что остаётся за границей

- Большой или намеренно вредоносный Export может занять заметное время, CPU и место на диске. Перед импортом стоит иметь свободное место и не запускать неизвестные экспорты от посторонних.
- Локальная БД содержит переписки в нормализованном виде. Системные резервные копии, индексаторы, malware или доступ к разблокированной учётной записи ОС не контролируются приложением.
- Пользователь сам выбирает папку для PNG/PDF: файлы в ней доступны программам и людям с доступом к этой папке. Share Preview по умолчанию скрывает имена, фрагменты и точные даты, но перед публикацией его нужно просмотреть целиком.
- Публичные установщики пока не подписаны и не notarized. CI собирает и проверяет artifacts, но подлинность дистрибутива для конечного пользователя потребует сертификатов Windows code signing и Apple Developer ID/notarization.

## Релизная проверка

Перед тегом поддерживающий должен запустить `npm run verify`, дождаться зелёной CI matrix и провести ручную приёмку на чистой системе: импорт fixture, экспорт безопасного PNG/PDF, удаление данных и повторный запуск. Черновик GitHub Release нужно сверить с `SHA256SUMS.txt` до публикации. Сертификаты и секреты добавляются только через GitHub Secrets; их нельзя коммитить, вставлять в issues или логировать.

Если найдена уязвимость, не публикуй личный Export или воспроизводящие данные в issue. Подготовь минимальный синтетический пример и свяжись с владельцем репозитория приватно.
